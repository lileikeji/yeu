# 单管理员运行手册

> 适用对象：当前唯一内容/系统管理员
> 适用阶段：V0.3 至 V1 单管理员模式
> 原则：先保证坐标和强时效事实正确，再追求内容数量

## 1. 操作边界

- 公开前台不需要学生账号；管理员账号只用于 `/admin` 和受保护 API。
- 管理员不代替学校确认录取、缴费、学籍、纪律、医疗或安全结论。
- 没有当年来源的报到安排、材料、校园卡流程、招新、快递外卖和商铺信息保持草稿或“待通知”。
- 地点名称、用途和开放状态的来源核验与坐标核验是两条独立链路；完成采点不会自动发布地点。
- 不在文档、工单、截图或聊天中保存明文密码、Cookie、会话 token、服务器 Key 或学生敏感信息。

## 2. 首次初始化与登录

生产首次初始化按 [DEPLOYMENT.md](./DEPLOYMENT.md#4-首次发布) 执行。关键要求：

1. 先确认 `NUXT_DATABASE_PATH` 指向 shared 数据库，而不是 release 内的临时文件。
2. 使用至少 12 个字符的随机管理员密码；生产优先临时注入 `NUXT_ADMIN_PASSWORD_HASH`。
3. 运行 `pnpm db:migrate`、`pnpm db:init` 和 `pnpm db:check`。
4. 初始化后从 `.env` 和 Shell 清除管理员明文密码及初始化哈希。
5. 通过 `/admin/login` 登录，确认未登录访问后台写接口会被拒绝。

本地验收凭据不能直接沿用到生产。密码轮换、旧会话撤销和备份步骤见 [DEPLOYMENT.md 的密码轮换章节](./DEPLOYMENT.md#41-管理员密码轮换与会话撤销)。

## 3. 每次维护开始前

1. 检查首页和 `/api/health`；生产环境必须返回 HTTP 200、`status=ok`、`database=ready`、`configuration=ready` 且 `issues=[]`。出现 503 时按问题码修复 HTTPS 站点 URL、高德配置、会话密钥或数据库，不带病维护内容。
2. 查看后台待处理反馈、临近过期内容、草稿和近期修改。
3. 检查学校官网、招生网和主管部门是否发布当年新通知；不要只依赖搜索摘要或转载提醒。
4. 报到季优先处理地图/流程 P0 问题，再处理营业时间、社团和排版问题。
5. 需要批量导入、迁移或密码轮换时先创建一致性备份，不在浏览器操作中途直接修改数据库文件。

## 4. 内容发布流程

### 4.1 先建立来源

来源记录至少填写标题、原始 URL、平台、发布主体、是否官方、等级、发布时间（如可知）、访问时间和支持的具体事实。按 [CONTENT_POLICY.md](./CONTENT_POLICY.md) 判断 A-E 等级；搜索平台摘要、群聊和普通用户内容只能作为线索。

### 4.2 建草稿与自检

1. 选择正确实体：地点、流程、指南、部门、社团或周边商铺。
2. 填写适用年份、受众（本科/专升本）、有效期和不确定项。
3. 把流程拆成动作、材料、地点和负责部门，不把旧年份安排复制为当年事实。
4. 关联有效来源；只有工作地图导入引用不等于正式事实来源。
5. 涉及地点时确认正式名称、别名、入口角色和 WGS84 坐标审核均完成。
6. 预览手机窄屏、来源链接、长名称和“待通知/过期”状态。

### 4.3 发布后验证

1. 从公开入口打开对应列表、详情、搜索结果和关联地图。
2. 确认公开 API 不返回草稿、内部备注、管理员信息或未授权联系方式。
3. 验证来源、最后核验时间、适用人群和纠错入口可见。
4. 涉及导航时在目标地图抽样核对，未核验坐标不得出现导航按钮或标点。
5. 记录变更摘要；发现关键错误时先下架/警示，再调查完整原因。

删除公开内容时优先归档或下架，避免失效分享链接和丢失审计依据。

## 5. 地图采点与审核

1. 从 [MAP_DATA_READINESS.md](./MAP_DATA_READINESS.md) 的 A 批次开始，不在现场临时创建同名地点。
2. 在 HTTPS 下打开 `/admin/field-observations`，选择正式地点和“主入口/场地点”。
3. 每次采集 3-5 个浏览器定位样本，填写标牌、入口方向和参照物，不记录同行学生或个人行程。
4. 弱网失败时可进入当前设备 IndexedDB 队列；恢复网络后逐条确认并同步，共用设备离场前清空队列。
5. 审核时核对有效精度不差于 25 米、样本离散、候选校界异常和现场说明；不通过就驳回，不手工绕过状态。
6. 首条观测批准后只会形成 `unverified` 候选；P0 点必须再完成一条同点位角色、相距不超过 20 米且满足采集独立性规则的观测，地点才会变成 `verified`。同方法采集至少间隔 30 分钟，且两条中至少一条来自浏览器定位或授权导入。
7. 批准坐标后仍要补正式地点来源、用途/开放状态和事实核验时间，满足全部发布门槛才可公开。

详细算法和隐私规则以 [FIELD_COORDINATE_VERIFICATION.md](./FIELD_COORDINATE_VERIFICATION.md) 为准。

## 6. 反馈与纠错

| 优先级 | 例子 | 操作目标 |
| --- | --- | --- |
| P0 | 可能错过报到/缴费、进入危险区域、隐私泄露 | 立即隐藏或警示，24 小时内核验 |
| P1 | 坐标明显错误、地点关闭、流程关键步骤错误 | 48 小时内核验 |
| P2 | 营业时间、联系方式、社团招新错误 | 7 天内处理 |
| P3 | 错别字、图片和体验建议 | 下一维护周期处理 |

处理时先保存原反馈与关联对象，再查原始来源或现场核验。无法确认的反馈保持待核实，不直接覆盖已发布事实。解决/驳回时记录结论，不公开提交者联系方式。宝塔计划任务每日运行 `pnpm feedback:cleanup`，失败必须告警。

## 7. 过期复核节奏

- 每月：处理反馈、失效链接、热门地点和公告。
- 每学期前：复核部门联系方式、网络/校园卡、快递点、商铺、社团和地点开放状态。
- 报到通知发布后 24-48 小时：更新年份、时间、材料、点位及本科/专升本差异。
- 报到季前：全量复核 P0 坐标、外部导航、联系方式、微信访问和断网说明页。
- 报到季中：优先处理临时变更、无结果搜索和 P0/P1 纠错。
- 报到季后：归档批次内容，不让旧流程继续显示为当前安排。

具体最长复核间隔见 [CONTENT_POLICY.md](./CONTENT_POLICY.md#5-核验时间与过期策略)。

## 8. 紧急下架

遇到错误坐标、错误报到/缴费信息、隐私泄露、侵权材料或现实安全风险时：

1. 立即将受影响内容下架/归档；范围不清时先发布有明确有效期的警示。
2. 保留原记录、来源和审计链，不先永久删除证据。
3. 检查搜索、关联页面、地图标点、导航按钮和 PWA 在线访问是否同步失效。
4. 向有权限的最新一手来源核验；无法确认时保持下架。
5. 修复后重新完成发布检查，并在必要时展示更正日期和说明。
6. 记录发现时间、影响范围、处置时间、依据和后续预防动作，不记录用户敏感数据。

Service Worker 在 V1 不缓存公开正文；断网只显示 `/offline.html`，因此不应承诺用户离线还能看到已下架内容。仍需检查浏览器/CDN 缓存头是否符合部署规范。

## 9. 发布、备份与恢复

- 日常代码发布、数据库迁移、Nginx、PM2、备份和恢复全部按 [DEPLOYMENT.md](./DEPLOYMENT.md) 执行。
- SQLite 只能有一个写实例，不启用 PM2 cluster；迁移前使用 `.backup` 创建一致性备份。
- 每次发布记录 commit SHA、迁移版本、检查结果、备份位置和回滚条件。
- 至少每季度从异机备份执行一次隔离恢复演练，验证地点、指南、管理员登录、发布/下线和媒体引用。
- 生产 PWA 验证 `sw.js` 不被长缓存，只预缓存 `/offline.html` 所需 CSS/图标/字体且不含 JavaScript；导航和 `/api/**` 均为 `NetworkOnly`，断网进入说明页。

## 10. 每次维护结束

1. 确认草稿没有误发布，紧急公告已设置失效时间。
2. 确认现场采点离线队列已同步或明确留在受控设备中。
3. 退出共用设备上的后台会话，不保存密码到浏览器或截图。
4. 记录尚待核验的事实、下一来源和处理期限。
5. 若执行了发布、迁移、凭据轮换或恢复，确认健康检查、公开主路径和监控均正常。
