# 仰恩大学新生入学指南系统路线图

> 文档版本：0.1
> 规划方式：以阶段成果和发布门槛为准，时间为单人开发的粗略估算
> 当前阶段：V0.3 内容与办事流程 Alpha，并行推进地图真实数据核验
> 关联文档：[PRD.md](./PRD.md)、[INFORMATION_ARCHITECTURE.md](./INFORMATION_ARCHITECTURE.md)

## 当前进度（2026-07-14）

- V0.1 工程与数据骨架已通过当前验收：Nuxt 前后台、SQLite 迁移、单管理员会话、来源与发布校验、PWA 生产构建、宝塔部署文档和自动化检查均已落地。
- 地图 Alpha 已具备搜索、分类、聚合、列表联动、响应式详情、OSM 社区候选校界、后台拾点与坐标审核流程。高德工作地图的 76 个标记点已作为无坐标草稿导入，学校官网平面图 47 项仅作文字索引。
- 验收库中的 76 个地点全部缺少坐标且保持草稿，坐标观测为 0，公开导航标点为 0。这是准确性门槛，不以近似坐标替代。
- 内容 Alpha 当前验收库有 24 条内容、36 条来源，其中 22 条内容已发布、2 条缺少可靠资料的生活指南保持草稿；另有 1 条已发布报到流程和 5 个结构化步骤。前台已提供普通关键词全站搜索。
- 已确认 2026 级新生 9 月 5 至 6 日报到、9 月 7 至 9 日入学教育、9 月 10 日上课；个人时段、报到点位、材料与接站安排仍待学校后续通知。
- 进入公开内测前仍需补齐：P0 地点坐标双重核验、校园卡现行流程、快递外卖站点与边界、2026 社团招新安排、现行到校交通信息和周边商铺核验。

## 1. 规划原则

1. 地图准确性和新生核心任务优先于内容数量、视觉包装和商业化。
2. 先建立内容结构、来源和核验机制，再批量采集资料，避免形成不可维护的散文集合。
3. 先让游客在手机和微信里完成任务，再建设学生账号、AI 和个性化能力。
4. 商家资料可以在 MVP 客观展示，但商家认领、优惠和推广必须在规则与审核能力成熟后开放。
5. 单人维护阶段尽量减少流程和角色复杂度，同时保留未来官方接入所需的来源、状态和修改记录。
6. 版本是否发布由验收门槛决定，不为赶日期带着错误坐标或过期报到信息上线。

## 3. V0.0：资料与基础决策

### 目标

把“需要做什么”和“哪些信息可信”转化为可执行清单，为地图与内容开发消除关键不确定性。

### 工作范围

- 确认产品正式名称、非官方声明、联系渠道和视觉使用边界。
- 建立 P0 地点清单：校门、报到点、宿舍、教学楼、行政服务、食堂、医务、校园卡/网络服务、快递、外卖取餐和交通点。
- 收集校内公开地图、官网通知、官方公众号内容、主流地图平台和社团公开资料。
- 为每条资料记录标题、URL/出处、平台、是否官方、访问日期、适用年份和待核实项。
- 确定地图供应商、授权/配额、坐标系和外部导航策略。
- 定义地点、流程、指南、部门、社团、来源和反馈的字段模板。
- 列出本科与专升本报到差异，无法确认的项目进入待核实清单。
- 规划现场采集：坐标、入口、文字路线、照片、营业时间和联系方式。

### 退出门槛

- P0 地点清单有负责人、来源和核验状态，不以模糊的“之后补”代替。
- 至少选定一个可用于开发测试的地图方案，并确认生产使用前还需完成的授权动作。
- 六类核心内容各有内容模板和第一批条目清单。
- 坐标系存储、展示和外部导航转换规则形成书面决策。
- 高风险未知项有明确核验路径，不把推测写成事实。

## 4. V0.1：工程与数据骨架

### 目标

建立适合持续开发、宝塔 Linux 部署和单人维护的最小工程基础，先打通数据读取与发布闭环。

### 前台范围

- Nuxt 应用布局、主题变量、响应式导航、错误页和基础 SEO。
- 首页、地图、流程、指南、校园、社团、周边、搜索和详情的路由占位。
- 通用加载、空数据、失败、离线和下架状态组件。
- PWA manifest、图标与缓存策略的初始配置。

### 后台与数据范围

- 数据库迁移和实体关系：地点、类别、指南、流程/步骤、部门、社团、来源、反馈、公告。
- 草稿、已发布、已归档状态和创建/修改/核验时间。
- 单管理员认证和受保护的管理路由。
- 地点、指南等至少一个实体的“新建 -> 预览 -> 发布 -> 下架”纵向切片。
- 开发/测试种子数据，不将未经确认的示例数据部署为真实内容。

### 运维范围

- 环境变量模板、生产构建、健康检查和结构化日志基础。
- 宝塔 Linux 的目标部署说明草稿，实际服务器信息后补。
- 数据库和媒体备份/恢复脚本或明确方案。
- CI 至少执行 lint、类型检查和生产构建。

### 退出门槛

- 新环境可按文档完成安装、构建和运行。
- 未登录无法执行后台写操作，密钥未写入仓库。
- 至少一个真实数据类型从后台发布后能在公开端读取。
- 数据库可迁移、可备份并在测试环境完成一次恢复验证。
- 公开路由结构与信息架构一致，不提前出现 AI、学生账号和商家认领入口。

## 5. V0.2：地图 Alpha

### 目标

验证产品最核心的“找到并看懂地点”能力；地图体验在此阶段优先于其他页面丰富度。

### 工作范围

- 校园默认视图、校内/周边范围、标点图层和类别筛选。
- 地点关键词与别名搜索。
- 标点聚合、选中态、摘要面板和独立地点详情。
- 用户定位授权、拒绝授权后的手动浏览和恢复校园视图。
- 外部地图导航、复制地址和文字路线降级。
- `/map?place=`、`q`、`category`、`scope` 深链接状态。
- 从地点详情、流程占位和指南占位进入地图并高亮。
- 地图脚本失败时的地点列表降级。
- 后台地图选点、经纬度输入、坐标系字段和发布校验。

### 内容范围

- 导入并核验首批 P0 地点。
- 每个地点至少具备名称、类别、范围、坐标/坐标系、详细位置、到达提示、来源和核验日期。
- 对宿舍、教学楼、报到点和校门进行重点坐标与入口核验。

### 测试重点

- 至少选取不同区域的样本点，与现场、可信地图或多来源交叉比对。
- Android、iOS Safari、微信内置浏览器分别验证地图、定位、深链接和外部导航。
- 窄屏、横屏、字体放大和长地点名称下，控件与详情面板不重叠。
- 弱网、地图服务限流和 JavaScript 错误时仍能看到地点文字信息。

### 退出门槛

- 测试用户能在 60 秒内完成指定宿舍/教学楼查找，成功率不低于 90%。
- P0 样本中不存在已知的严重坐标偏移或错误导航目的地。
- 拒绝定位不阻断核心流程；地图失败时可查文本详情。
- 分享链接在普通浏览器和微信内打开后能恢复目标地点。
- 后台无法发布缺少名称、类别、坐标或坐标系的地点。

## 6. V0.3：内容与后台 Alpha

### 目标

让六类新生任务拥有结构完整、可关联、可维护的真实内容，并让单人管理员能持续更新。

### 工作范围

- 首页六个快捷任务和当前有效公告。
- 报到流程列表/详情、本科与专升本受众标记、材料和地点关联。
- 校园卡与网络、宿舍/教学楼、快递外卖等指南列表/详情。
- 校园简介、常用部门和部门详情。
- 社团分类、详情、招新状态和有效期。
- 周边商铺列表/地图、客观详情和核验状态。
- 普通关键词全站搜索，覆盖所有公开实体。
- 无需登录的纠错反馈和后台处理状态。
- 后台各实体 CRUD、预览、发布、归档、来源关联和复核日期。
- 公告生效/失效时间和关联内容。

### 内容门槛

- 报到：至少一套完整通用流程；本科/专升本差异已核实或显著标记待官方通知。
- 地图：P0 地点清单全部录入并完成双重核验。
- 校园卡与网络：首次办理、常见问题和服务地点可执行。
- 快递外卖：站点/取餐点、服务范围、时间与临时变化机制完整。
- 社团：只发布取得公开来源或明确同意的联系方式，招新状态可过期。
- 周边商铺：不虚构评分，不开放认领、优惠、推广或交易。
- 所有规则性/时效性核心内容展示来源和最后核验日期。

### 退出门槛

- 六类任务均可从首页无需登录完成至少一条端到端路径。
- 搜索常用词、简称和预设无结果词测试通过；无结果有明确替代入口。
- 管理员可在不修改代码的情况下完成所有核心内容更新和下架。
- 过期招新、公告和报到批次不会继续以进行中状态公开。
- 反馈提交具备基础限流，后台能关联条目并完成处理。
- 未经审核的反馈或草稿不会被公开端检索到。

## 7. V0.9：新生内测

### 目标

在公开发布前集中发现地图、内容、微信兼容和新生理解偏差。

### 建议测试参与者

- 5-8 名对校园熟悉的在校生，用于核验地点和校内称呼。
- 8-12 名不熟悉校园的新生或模拟新生，用于任务可用性测试。
- 至少 2 名专升本学生，用于核对受众差异。
- 内容维护者本人，完整演练发布、纠错和紧急下架。

### 内测任务

- 找到指定宿舍、教学楼、快递点和校园卡服务点。
- 根据报到流程说清下一步、材料与地点。
- 在微信中打开被分享的地点和流程深链接。
- 拒绝定位后继续查找地点。
- 模拟断网导航进入 `/offline.html`，确认不会显示旧指南正文，并可在恢复网络后重试。
- 发现一处模拟错误并提交纠错，由后台处理完成。
- 安装 PWA（支持设备）并验证启动、更新与离线提示。

### 退出门槛

- 阻断级问题和严重内容/坐标错误为 0。
- 地点查找与报到任务成功率均不低于 90%。
- 微信内核心任务通过，受限能力均有实际可执行的降级路径。
- PWA 页面导航和内容 API 保持 `NetworkOnly`；断网只显示说明页，恢复网络后可取得当前内容。
- 隐私、来源、非官方声明和反馈渠道可见且文案经过确认。
- 后台备份恢复、管理员凭据轮换和紧急下架完成演练。

## 8. V1.0：MVP 公开版

### 发布内容

- 精细校园与周边地图、地点搜索/筛选/详情和外部导航。
- 报到流程、宿舍/教学楼、校园卡与网络、快递外卖、周边商铺和社团招新。
- 校园简介、常用部门、站内普通搜索和纠错反馈。
- 单管理员内容后台、来源记录、发布状态、有效期和公告。
- PWA 基本安装、断网说明页与微信内访问降级；V1 不承诺离线正文。

### 明确不随 V1.0 发布

- 学生账号和学号认证。
- AI 问答或 AI 检索。
- 商家认领、优惠、推广位、支付、评论与评分。
- 原生 App、微信小程序和室内实时导航。
- 学校部门账号、多角色审批和官方系统接口。

### 上线检查

- 域名、HTTPS、备案/合规要求和地图域名白名单完成。
- 生产环境密钥、数据库、对象存储/媒体、日志和备份正确配置。
- 404、500、离线、地图失败、定位拒绝和内容下架状态通过。
- 核心来源链接、联系电话、时间和坐标完成最后复核。
- 公开非官方声明、隐私说明、内容纠错和联系方式。
- 监控至少覆盖站点可用性、服务错误、地图配额和备份结果。
- 建立报到季值守清单与错误信息紧急下架流程。

## 9. V1.1：质量与内容运营

V1.1 不以增加大功能为目的，优先根据真实使用改进质量：

- 根据无结果搜索词补充别名、同义词和缺失内容。
- 后台增加到期/待复核提醒、批量筛选和内容质量检查。
- 优化地图标点密度、筛选、返回状态、长名称和低端设备性能。
- 改进 PWA 更新提示和微信受限操作说明；评估带缓存时间、版本失效和强时效内容排除规则的后续离线正文方案。
- 建立每学期内容复核、报到季前专项复核和商铺停业检查。
- 在不采集精确轨迹的前提下完善匿名任务漏斗。
- 视反馈增加本机收藏、最近访问和报到清单，不引入账号依赖。

V1.1 的发布判断应基于数据和反馈；避免仅为了版本号增加低使用率入口。

## 10. V1.5：商家合作试点

### 前置条件

- V1.0 至少稳定运行一个完整使用高峰，地点和反馈机制可靠。
- 商业内容政策、收费/退款规则、投诉渠道、隐私说明和运营主体明确。
- 能验证商家主体或店铺控制权，并保留认领与修改记录。
- 自然结果排序、推广展示和学校非背书声明已书面化。

### 试点范围

- 商家认领申请、管理员审核、联系方式验证和资料修改申请。
- 有明确有效期和使用条件的优惠信息。
- 数量受控、显著标有“推广”的推广位。
- 推广与自然地点详情分离统计，用户可反馈虚假或过期信息。
- 管理后台完成审核、驳回、暂停、到期和投诉处理。

### 仍不建议同时建设

- 复杂广告竞价系统、用户画像投放、站内支付和自动结算。
- 未经人工审核的商家自助直接发布。
- 付费影响公共服务地点、报到信息或自然搜索相关性。

### 试点退出标准

- 所有推广内容可识别、可追踪、可到期、可紧急下架。
- 认领资料修改不覆盖学校官方或现场核验事实而无审核。
- 投诉与纠错有明确处理时限，试点未显著降低用户对指南的信任。

## 11. V2.0：学生账号与 AI 检索

### 前置条件

- 结构化内容、来源和核验日期覆盖稳定，AI 能引用可靠资料而非自由编造。
- 明确账号用途、身份方式、隐私政策、数据保留与注销流程。
- 有能力监控模型成本、质量、安全和敏感问题，并提供人工纠错。

### 账号范围

- 可选学生账号，不登录仍可使用 V1.0 所有公共内容。
- 跨设备收藏、报到清单同步、历史记录控制和数据导出/注销。
- 如引入学号或学校身份认证，必须获得相应授权并单独进行安全评估。

### AI 检索范围

- 使用经审核内容库检索并回答新生问题。
- 每个事实性回答展示引用来源、核验日期和相关原文入口。
- 不确定或当年通知未发布时明确说明，优先引导官方渠道。
- 地点回答可打开地图，流程回答可定位具体步骤。
- 不代替学校做收费、录取、纪律、医疗或安全方面的最终决定。
- 提供普通关键词搜索的永久降级入口。

### 发布门槛

- 建立覆盖六类核心任务的评测集，事实正确、引用匹配和拒答策略达标。
- 提示注入、越权数据读取、隐私泄露和恶意内容测试通过。
- 用户可删除历史和账号；模型输入/日志保留范围清晰可见。
- 成本或模型故障时，公共页面与普通搜索不受影响。

## 12. V3.0：官方协作准备

只有出现明确校方或部门合作意向后启动，避免提前构建无用户的复杂权限系统。

### 可能范围

- 学校、部门、学生团队等角色与最小权限。
- 编辑、复核、批准、定时发布、紧急下架的审核流。
- 完整修改历史、操作审计、来源版本和责任人。
- “官方确认”标识及其授予/撤销规则，和学生团队内容清晰区分。
- 部门自助维护指定内容，不可越权修改其他部门或商业内容。
- 数据导入、导出、备份、交接和服务连续性方案。
- 安全、无障碍、合规、等保/备案等要求按合作范围专项评估。

### 成功标准

- 官方内容与非官方整理内容身份明确，用户不会混淆。
- 发布、撤回和审计责任可追溯。
- 系统可从个人维护平滑转向团队或学校共同维护，无需破坏既有公开链接与数据。

## 13. 跨阶段内容运营节奏

### 常规周期

| 时间点 | 重点动作 |
| --- | --- |
| 每月 | 处理反馈、检查失效链接、复核高访问地点与公告 |
| 每学期前 | 复核部门时间、网络/校园卡流程、快递点、商铺和社团资料 |
| 报到通知发布后 24-48 小时 | 更新当年流程、日期、材料、报到点及本科/专升本差异 |
| 报到季前 | 全量核验 P0 坐标、导航、联系方式、微信和弱网流程 |
| 报到季中 | 监控临时变更、无结果搜索与高频纠错，快速发布公告 |
| 报到季后 | 归档批次内容、总结问题并调整下一周期清单 |

### 内容状态建议

```text
草稿 -> 已核验 -> 已发布 -> 待复核 -> 已更新/已归档
                    |             ^
                    +-> 已过期 ---+
```

MVP 数据模型至少保留草稿、已发布、已归档；“已核验、待复核、已过期”可以由核验日期和有效期推导，避免状态组合失控。
