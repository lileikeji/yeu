> 对象：本仓库全部架构模块（前台 67 页、后台 22 个模块、248 个 API、65 张表、AI 问答链路、小程序只读端）。

## 一、裁决

**资产是「仰恩这一平方公里的可核验事实层 + 一句能引用的答案」。拖住它的是 5 个长在架构外面的活动页、4 套并行的身份系统、1 个 8706 行的 `service.ts` 和 1 个 3866 行的 Vue 单文件。**

代码质量不差：服务端分层成立（248 个 handler 平均 27 行，业务在 `server/modules/` 的 27 个目录），后台统一走 `useAdminRequest` + 15 个中间件兜底。问题不在写法，在取舍、收敛与可交接性。

### 明确不做的四件事

1. **不重写**：13,500 行 assistant 里有大量确定性规则与知识治理，重写等于重做治理，按 strangler 五批迁移。
2. **不做社区**：Yik Yak 两次关停的教训是排序机制放大攻击，不是审核不够。
3. **不做第二向量库 / 多模型投票 / 全量微调**：分别败在一致性、成本（单问已 2-4 次调用）、数据规模。
4. **不在小程序加功能**：快照里小程序侧 AI 调用 11 次（全站 3,711），先加埋点，3 个月无周活下线。

## 三、需求错位

三条证据指向同一结论：**IA 描述的是「我们做了哪些模块」，不是「用户此刻要解决什么」。**

1. 搜索被强制走 AI 模式，站内结果要多点一次。
2. `/transport`、`/clubs`、`/competition` 在移动主路径上没有入口。
3. 最高频的长句提问是班委批量算综测（30/29/21/19×4 次…），产品给的却是一个自由文本框。

结论：把「综测长句」做成**表单 + 规则引擎 + 条款引用**，是投入产出最高的一件事，不是 prompt 优化。

## 四、架构结论

- **四套身份各写一遍 cookie + CSRF**（admin / judge / user / admin-device）：合到一套 session 表 + 一张权限表。
- **`server/utils` 是垃圾桶**：按职责拆到 `modules/`。
- **内容两条真相**：DB 与 `data/seeds` 各有一份，靠 normalizer 对齐；应当 seeds 只做首次导入，之后单一来源。
- **性能口径不是 QPS，是「每秒总 DB 毫秒数」**：单条 SQL 的预算要按并发反推。
- **质量闸门三绿一红**：测试、typecheck、构建绿，`pnpm lint` 红；而红的那条正好是发布唯一没走的脚本。

## 五、目标 IA

- 导航三层：底栏 5 项（首页 / 地图 / 办事 / 生活 / 我的）、桌面 6 项（多「校园」）、后台 22 项。
- 「我在哪」必须可计算：前缀映射表 + `aria-current`，不用 `startsWith` 单层判断。
- 首页回答三个问题：现在要办什么、去哪儿办、办不成找谁。
- 地图是枢纽：选点不能藏在默认收起的面板后；面板只挂一份。
- 一致性债一次性清：骨架屏、加载条、组件统一（`UButton` / `UModal` / `UTable`）、暗色对比度。

## 六、AI 链路目标架构

一条可测管线，`service.ts` ≤800 行：normalize → route → retrieve → compose → verify → cache。

- 五批 strangler，每批独立可回滚；只有 B5 允许行为变化，必须与验收用例同批提交并 bump `ASSISTANT_CACHE_VERSION`。
- 评测门禁用 340 条金标三层（事实正确 / 引用可点 / 拒答得当）。
- 引用不许兜底：没有来源就返回 `citationStatus: 'none'`，不拿同实体其它结论顶替。
